# ADR-0015: Rails 8 Authentication Generator ベースの認証基盤

## コンテキストと課題

認証機能がなく、すべての Todo が誰でも閲覧・操作できる状態だった。ユーザー認証を導入するにあたり、どの認証フレームワーク/手法をベースにするかを決定する必要があった。

API-only 構成の Rails アプリケーションであること、ソーシャルログインは Phase 2 で後付けする方針であることが制約条件。

## 検討した選択肢

### 選択肢1: Devise

Rails で最も広く使われる認証 gem。ユーザー登録、ログイン、パスワードリセット、メール確認などの機能がフルセットで提供される。

- 良い点: 成熟したエコシステム、豊富なドキュメントと拡張 gem（devise-jwt, OmniAuth 連携など）
- 悪い点: API-only 構成との相性に難がある（ビュー前提の設計）、設定がブラックボックス化しやすい、Rails 8 の方向性と乖離する

### 選択肢2: Rails 8 Authentication Generator

`bin/rails generate authentication` で User/Session/Authentication concern を生成する Rails 公式の手法。生成されたコードはアプリケーションに直接配置され、完全に可読・可変。

- 良い点: Rails 公式路線で長期メンテナンス性が高い、生成コードが透明で理解しやすい、必要に応じたカスタマイズが容易
- 悪い点: 生成されたコードを API-only 向けに手動で調整する必要がある（ビュー層の除去、JSON レスポンス化）、Devise ほど機能がリッチではない

### 選択肢3: JWT ライブラリ（jwt gem / devise-jwt）

JWT トークンをベースにしたステートレス認証。`Authorization: Bearer` ヘッダーでトークンを送受信する。

- 良い点: ステートレスでスケーラブル、API 構成との相性が良い
- 悪い点: トークンの無効化（ブラックリスト管理）が複雑、リフレッシュトークンのフローが必要、セキュリティ面の考慮事項が多い

### 選択肢4: 手動実装

`has_secure_password` をベースに認証ロジックをゼロから実装する。

- 良い点: 完全にコントロール可能、不要な依存がない
- 悪い点: 車輪の再発明、セキュリティ面でのレビュー負担が大きい、パスワードリセットやセッション管理の実装コストが高い

## 決定

**選択肢2: Rails 8 Authentication Generator** を採用する。

Rails 公式路線に乗ることで、長期的なメンテナンス性と透明性を確保する。生成されるコードはアプリケーション内に直接配置されるため、API-only 向けの調整（JSON レスポンス化、ビュー層の除去）が容易。OmniAuth によるソーシャルログインも Devise 非依存で後付け可能なため、Phase 2 への拡張パスも確保される。

## 結果

### 良い影響

- 認証ロジックがアプリケーションコード内に透明に存在し、デバッグ・カスタマイズが容易
- Rails のバージョンアップに追従しやすい（公式推奨の手法）
- OmniAuth を Devise 非依存で後付けできるため、Phase 2 のソーシャルログイン対応がスムーズ

### 悪い影響

- 生成されたコードを API-only 向けに手動で調整する作業が必要だった（ビュー層の除去、JSON レスポンス化）
- Devise のような豊富なプラグインエコシステムは利用できない
